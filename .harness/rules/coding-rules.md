# 编码规则

## 通用原则

1. 优先沿用项目现有目录、命名、依赖注入和错误处理模式。
2. 改动范围必须贴合当前任务，避免无关重构和全仓格式化。
3. 公开契约默认保持兼容，包括 API 响应、事件格式、配置项、CLI 参数和数据库 schema。
4. 新增依赖必须满足三个条件：现有工具无法合理完成、依赖维护状态可信、收益高于引入成本。
5. 错误必须可定位、可测试，不向用户暴露内部堆栈、密钥、路径或供应商细节。
6. 配置必须通过明确入口读取，不在业务代码中硬编码环境差异。
7. 复杂逻辑必须有清晰边界：协议适配、业务编排、领域规则、外部系统访问和通用工具不能混在一起；具体目录名以项目既有结构为准。

## 结构设计和职责归属

1. 写代码前先阅读项目现有目录和相邻实现，判断新代码应放在哪里，并在交付中说明落点理由。
2. 不强制项目使用固定目录名；`api`、`service`、`domain`、`repository`、`infra`、`components`、`hooks`、`utils` 等只作为常见职责示例。
3. 按职责而不是按便利性放代码：协议适配、业务编排、领域规则、外部系统访问、状态管理、UI 展示和测试应有清晰边界。
4. `utils`、`helpers`、`shared` 这类目录只适合放业务无关的通用能力；包含业务名词、权限、状态流转、计费、审批、检索策略或领域异常的逻辑应放到对应业务模块。
5. 协议入口只做协议适配和编排入口，不承载复杂业务规则；业务规则应靠近业务概念本身。
6. 外部系统访问应被隔离在清晰边界内，避免第三方 SDK、数据库查询、文件系统细节散落到业务逻辑中。
7. 前端代码应先判断是页面入口、业务组件、复用组件、状态逻辑、数据访问还是通用工具；具体目录按项目已有约定决定。
8. 新增目录前先检查项目已有模式；没有模式时按业务能力和变化方向设计，而不是机械套用固定分层。
9. 如果选择不拆分或不引入新目录，必须说明当前复杂度为什么仍适合保持简单。

## 设计模式使用

1. 只有存在真实变化点时才引入设计模式，不为简单分支制造抽象。
2. 多种可替换算法、供应商、检索策略、排序策略或计费策略优先考虑 Strategy。
3. 第三方 SDK、外部 API、文件系统、消息队列和模型供应商差异优先用 Adapter 隔离。
4. 复杂对象创建、环境差异或按配置选择实现时可使用 Factory。
5. 数据访问边界使用 Repository 或 Gateway，避免业务层直接散落查询细节。
6. workflow、状态机、审批流或多阶段任务可使用 State、Command 或 Pipeline，但必须保持节点输入输出可测试。
7. multi-agent 工具和 handoff 应通过明确接口、schema 和策略对象表达，不把所有判断写进 prompt 字符串。
8. 引入模式时必须说明它解决的变化点，并保持文件和类名能表达业务含义。

## 文件大小和拆分

1. 业务源码文件默认最大 800 行，超过前必须按业务能力、层级或职责拆分。
2. 单个函数默认不超过 100 行；超过时优先提取带业务含义的私有函数、策略或对象。
3. 单个类默认不超过 500 行；超过时检查是否混入多种职责或多个变化点。
4. 拆分优先按业务维度、职责边界或变化点，不要把所有杂项塞进 `helpers.py`、`utils.py` 或单个“大文件”。
5. 超过 800 行的文件在审查中默认视为需要修复；确有例外时必须在交付说明中解释原因。
6. 例外文件包括生成文件、锁文件、迁移脚本、测试快照、大型静态配置、文档和供应商复制文件。
7. 新增代码前应估算目标文件大小；如果会让文件超过上限，先设计拆分方案再实现。

## Python 后端

1. 新增函数和公共方法必须带类型签名。
2. FastAPI router 中只做请求解析、权限入口、调用业务编排逻辑和响应转换。
3. 业务规则放在项目中承载业务概念的模块内，不直接绑定 HTTP、数据库或第三方 SDK。
4. 外部 I/O 使用超时、错误映射和可观测日志；不要吞掉异常。
5. 对结构化数据使用 Pydantic、标准解析器或库 API，不用脆弱的字符串切分。
6. RAG 代码必须区分 document loading、chunking、embedding、retrieval、reranking 和 generation。
7. workflow 代码必须明确节点输入输出、重试策略、幂等性和失败恢复方式。
8. multi-agent 代码必须明确 agent 职责、可用工具、handoff 条件和终止条件。

## 前端

1. 复用现有组件、样式系统、路由和状态管理方式。
2. 用户路径必须覆盖 loading、empty、error、success 和权限不足状态。
3. 表单必须处理校验、提交中、失败重试和重复提交保护。
4. UI 文案要表达用户任务，不暴露内部实现或调试信息。
5. 不使用 inline style，除非项目已有约定或该样式必须由运行时计算。
6. 组件拆分以真实复用和清晰状态边界为准，不为单次使用制造抽象。
7. 前端调用 API 时要处理非 2xx、超时、取消和后端错误码。

## 数据和迁移

1. schema 变更必须说明兼容策略、默认值、回填和回滚方式。
2. destructive migration 必须有人工确认和备份或恢复路径。
3. 查询变更要考虑索引、分页、排序稳定性和 N+1 风险。
4. 写入逻辑必须考虑幂等性、并发和重复请求。

## 质量门禁

1. 行为变化必须配套测试或说明无法测试的原因。
2. 安全、权限、支付、删除、批量操作必须有失败路径测试。
3. 代码完成后删除无用日志、注释掉的代码和临时开关。
