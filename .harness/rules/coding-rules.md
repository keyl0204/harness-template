# 编码规则

## 通用原则

1. 优先沿用项目现有目录、命名、依赖注入和错误处理模式。
2. 改动范围必须贴合当前任务，避免无关重构和全仓格式化。
3. 公开契约默认保持兼容，包括 API 响应、事件格式、配置项、CLI 参数和数据库 schema。
4. 新增依赖必须满足三个条件：现有工具无法合理完成、依赖维护状态可信、收益高于引入成本。
5. 错误必须可定位、可测试，不向用户暴露内部堆栈、密钥、路径或供应商细节。
6. 配置必须通过明确入口读取，不在业务代码中硬编码环境差异。
7. 复杂逻辑必须有清晰边界：API 层负责编排，service/domain 层负责业务，infra 层负责外部系统。

## Python 后端

1. 新增函数和公共方法必须带类型签名。
2. FastAPI router 中只做请求解析、权限入口、调用 service 和响应转换。
3. 业务规则放在 service/domain，不直接绑定 HTTP、数据库或第三方 SDK。
4. 外部 I/O 使用超时、错误映射和可观测日志；不要吞掉异常。
5. 对结构化数据使用 Pydantic、标准解析器或库 API，不用脆弱的字符串切分。
6. RAG 代码必须区分 document loading、chunking、embedding、retrieval、reranking 和 generation。
7. workflow 代码必须明确节点输入输出、重试策略、幂等性和失败恢复方式。
8. multi-agent 代码必须明确 agent 职责、可用工具、handoff 条件和终止条件。

## 前端

1. 复用现有组件、样式系统、路由和状态管理方式。
2. 用户路径必须覆盖 loading、empty、error、success 和权限不足状态。
3. 表单必须处理校验、提交中、失败重试和重复提交保护。
4. UI 文案要表达用户任务，不暴露内部实现或调试信息。
5. 不使用 inline style，除非项目已有约定或该样式必须由运行时计算。
6. 组件拆分以真实复用和清晰状态边界为准，不为单次使用制造抽象。
7. 前端调用 API 时要处理非 2xx、超时、取消和后端错误码。

## 数据和迁移

1. schema 变更必须说明兼容策略、默认值、回填和回滚方式。
2. destructive migration 必须有人工确认和备份或恢复路径。
3. 查询变更要考虑索引、分页、排序稳定性和 N+1 风险。
4. 写入逻辑必须考虑幂等性、并发和重复请求。

## 质量门禁

1. 行为变化必须配套测试或说明无法测试的原因。
2. 安全、权限、支付、删除、批量操作必须有失败路径测试。
3. 代码完成后删除无用日志、注释掉的代码和临时开关。
