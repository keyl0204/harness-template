# 测试规则

## 测试目标

测试必须保护用户可感知行为、业务约束、权限边界和关键失败路径。
不要为了覆盖率编写只验证实现细节的脆弱测试。

## 强制要求

1. bugfix 必须补回归测试，并证明旧失败场景已被覆盖。
2. 新增业务规则、业务编排或领域约束必须有单元测试。
3. 新增 API 必须有路由测试或集成测试，覆盖状态码、响应体和错误路径。
4. 权限逻辑必须有允许访问和拒绝访问两类测试。
5. 数据库写入、批量操作、删除和外部副作用必须测试失败和幂等场景。
6. RAG、workflow、multi-agent 逻辑必须测试空输入、工具失败、超时或无结果路径。
7. 测试失败时不能标记任务完成。

## 测试分层

### 单元测试

- 验证纯业务规则、数据转换、权限判断、状态转移和错误映射。
- Mock 外部 I/O，但不要 Mock 被测模块内部实现。

### 集成测试

- 验证 API 路由、依赖注入、数据库访问、外部客户端边界和配置。
- 使用最小真实路径，避免把所有逻辑都挤进端到端测试。

### 前端测试

- 验证用户行为：输入、提交、错误展示、空状态、权限不足和导航。
- 避免依赖 DOM 内部结构；优先使用用户可见文本、角色和交互。

### 回归测试

- 测试名要表达修复的失败模式。
- 断言必须能在 bug 复现时失败。

## 测试数据

1. 测试数据必须最小、明确、可读。
2. 不使用生产数据、真实密钥或真实个人信息。
3. 时间、随机数、网络和外部服务必须可控。
4. 快照测试只用于稳定结构，不用于掩盖复杂断言。

## 命令

按改动范围选择最小有用命令：

```bash
make test
make check
```

Python 项目可按需运行：

```bash
uv run pytest
uv run ruff check .
uv run pyright
```

前端项目可按需运行：

```bash
pnpm run test
pnpm run lint
pnpm run typecheck
pnpm run build
```

## 质量门禁

1. 测试命名应表达它保护的行为。
2. 断言必须验证结果，不只验证函数被调用。
3. 测试失败信息应能帮助定位问题。
4. 新增测试不能依赖执行顺序或共享脏状态。
5. 无法运行的测试必须说明原因和替代验证。
