# 文档边界规则

## 目标

保持 Harness 协作规则、项目事实和任务状态各自独立，避免规则、需求、实现细节互相污染。

## `.harness/` 可以包含

1. Agent 角色协议、模型配置、输入输出格式和工作边界。
2. Codex 工作流、协作步骤、验证要求和交接规则。
3. AI 工程规则，例如编码、审查、安全、测试、文档边界。
4. Skills 的可复用执行方法，但不写入当前项目的具体业务需求。
5. 当前任务状态、handoff、功能索引和自动化脚本说明。

## `docs/` 可以包含

1. 产品目标、用户故事、验收标准和路线图。
2. 领域术语、业务规则、权限模型和状态机。
3. 架构概览、模块边界、API 规范、数据库设计和集成说明。
4. 运维手册、部署流程、回滚流程和 ADR。
5. 对外可审计的技术决策，而不是 Codex 内部执行提示。

## 根目录文件可以包含

1. `AGENTS.md`：项目级入口、文档路由和完成标准。
2. `README.md`：人类用户的项目介绍、启动和验证方式。
3. `pyproject.toml`、`package.json`、`Makefile`：工程配置和命令入口。

## 禁止

1. 不要在 PRD 中写 Codex 工作流或子 Agent 分工。
2. 不要在 Skill 中写具体客户需求、临时任务状态或一次性实现计划。
3. 不要把 `AGENTS.md` 写成完整需求文档。
4. 不要在 Agent 角色协议中写项目业务规则、API 契约或数据库 schema。
5. 不要在 `docs/product/` 中写 AI 角色分工、模型选择或工具调用策略。
6. 不要把临时调试记录写进架构文档。

## 更新触发器

1. 业务行为、用户路径或验收标准变化：更新 `docs/product/`。
2. 术语、权限、状态流转或领域约束变化：更新 `docs/domain/`。
3. 模块边界、API、数据库、集成或部署方式变化：更新 `docs/architecture/` 或 `docs/operations/`。
4. Agent 职责、模型、工作流、规则或验证方式变化：更新 `.harness/`。
5. 新增常用命令或启动方式变化：更新 `README.md` 和必要的运维文档。

## 冲突处理

1. `docs/` 与代码不一致时，先判断代码是否实现了新事实；不能直接让文档迁就错误实现。
2. `.harness/` 与 `AGENTS.md` 不一致时，以更具体的规则文件为准，并同步入口文档。
3. 需求不明确时，不在规则文件中补业务假设；应在产品或领域文档中明确。
