# 审查规则

## 审查立场

审查优先发现会造成错误结果、回归、安全问题、数据损坏、不可运维或测试缺口的事实问题。
不要把个人偏好、风格建议或无关重构放在必须修复项里。

## 严重等级

- P0：阻塞发布，或可能造成数据破坏、安全事故、资金损失、合规事故。
- P1：主要用户路径失效、权限绕过、严重回归或无法恢复的任务失败。
- P2：重要问题，应在合并前修复，例如边界条件错误、缺失关键测试、错误处理不充分。
- P3：轻微可维护性、可读性或局部体验问题，不阻塞合并。

## 审查流程

1. 先理解用户需求、验收标准和相关文档。
2. 查看实际 diff，不根据文件名或意图猜测实现正确。
3. 优先沿调用链审查输入、状态变化、持久化、副作用和输出。
4. 对每个发现给出可复现失败模式。
5. 区分“必须修复”和“建议优化”。
6. 没有发现问题时明确说明，并列出仍未覆盖的验证范围。
7. 检查新增代码是否经过结构设计，落点是否符合项目既有架构和职责边界。
8. 检查业务源码文件是否超过 800 行；超过且未说明例外时列为必须修复。

## 专项检查

### 后端

- API 是否保持兼容，状态码和错误格式是否符合约定。
- 权限、租户、数据范围和资源归属是否在服务端校验。
- 数据库查询是否有分页、排序稳定性、索引和事务边界。
- 外部服务失败是否有超时、重试限制和错误映射。
- 业务规则是否放在承载业务概念的模块内，而不是散落在协议入口、通用工具、外部适配或展示组件中。
- 供应商、算法或状态变化点是否被合适的 Strategy、Adapter、Factory、Repository 或 State/Pipeline 边界隔离。

### 前端

- 用户关键路径是否处理 loading、empty、error、success。
- 表单是否防重复提交，错误是否可恢复。
- API 错误、权限不足和会话过期是否有明确反馈。
- 响应式布局是否可能出现遮挡、溢出或不可点击区域。
- 页面入口、业务组件、复用组件、状态逻辑、数据访问和通用工具是否职责清晰；具体目录名以项目约定为准。
- 组件文件是否过大，是否应按业务区块、状态逻辑或数据访问拆分。

### AI/RAG/workflow/multi-agent

- Prompt、工具调用和上下文拼接是否可能泄露敏感数据。
- RAG 检索是否有来源、过滤条件和空结果处理。
- workflow 是否定义失败恢复、幂等性和节点间数据契约。
- multi-agent 是否定义 handoff 条件、停止条件和工具边界。

## 必要证据

1. 引用精确文件和行号。
2. 说明触发条件、失败结果和影响范围。
3. 给出能解决问题的最小修正方向。
4. 不引用不存在的测试或未运行的验证。

## 输出格式

```text
结论：通过 / 不通过

必须修复：
- [P1] 文件:行 - 问题、失败模式、最小修正

建议优化：
- [P3] 文件:行 - 建议

测试缺口：
- ...

剩余风险：
- ...
```
